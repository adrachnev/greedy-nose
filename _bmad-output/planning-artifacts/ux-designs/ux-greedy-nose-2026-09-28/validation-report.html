greedy-nose mocks/ — UX Validation Report

mocks/ (22 screens) validated against REQUIREMENTS.md — no DESIGN.md/EXPERIENCE.md spine exists yet for this project, so mocks/ was validated directly as the UX artifact

The mocks are in good shape for the bulk of REQUIREMENTS.md — R9, R13/R13a, R14/R8a, R17/R17a, R19, R20/R20a wording, R23/R23a on the debit list, R25/R26/R26a's onboarding behavior, the R8 anti-pitfall check, and all four already-tracked "known mock gaps" are correctly and consistently represented, with no undisclosed drift in either direction. The one sharp gap is R12a's "no rule" notification wording: the string rewritten in the 2026-09-24 revision specifically to stop implying an unfamiliar payee was never propagated into the two mock files that quote it — and those two quotes don't even agree with each other. A handful of smaller citation/terminology staleness items round out that pass.

The accessibility pass (not sourced from REQUIREMENTS.md, run as an ad-hoc lens) found a design system that is more accessibility-literal than most mockup sets: every good/bad state is backed by a redundant text label (never color alone), and touch targets are 44px by default via shared CSS classes — so the colorblind-with-no-secondary-cue failure mode does not occur. What is missing is contrast discipline: the --good/--bad/--accent tokens fail WCAG AA (3.3–4.0:1 against a 4.5:1 requirement) against their own tinted backgrounds and against white in light mode, hitting the Good/Bad pills, the classification toggle, and the primary Save button specifically — plus a handful of controls authored as plain non-semantic <div>s with no button role. Dark mode is unaffected throughout. None of the accessibility findings risk the app's one unacceptable failure (a charge that silently never notifies) since every state is still backed by redundant text — they degrade legibility/operability, not correctness.

critical

R12a's "no rule" notification body is stale and self-contradictory across the two mocks that quote it

mocks/03-debit-detail.html:29, mocks/05-notification.html:24 — R12a
REQUIREMENTS.md (revised 2026-09-24) fixes this string to "You haven't reviewed this payee yet." — specifically because the old wording falsely implied the payee itself was unfamiliar. 03-debit-detail.html's comment still reads "This payee is new — you haven't reviewed it yet."; 05-notification.html's comment reads a third, different string: "New payee — you haven't seen this one before." Neither file was updated for the revision, and the two disagree with each other and with the spec. No mock screen for the "no rule" case is ever fully drawn, so these two comments are the only place this reason's wording lives in mocks/ — the single most likely spot to ship the wrong push copy.
Fix: Replace both comments with the canonical "You haven't reviewed this payee yet." Consider drawing a 05a-notification-no-rule.html mirroring 05/05c so all three R12a reasons have an actual rendered mock, not just prose.

Accessibility review

review-accessibility.md

Ad-hoc lens, not sourced from REQUIREMENTS.md. Contrast ratios computed from the literal hex/rgba values in mocks/style.css using the WCAG relative-luminance formula, not measured on a device. No finding rated critical: every state is still backed by redundant text, so none risk the app's one unacceptable failure (a charge that silently never notifies) — these degrade legibility/operability, not correctness. Dark mode is comfortably AA-compliant throughout; every finding below is a light-mode-only gap.

high

Primary CTA button text (white-on-accent-blue) fails WCAG AA, ~3.65:1 vs 4.5:1 required

mocks/style.css .btn-primary — every primary-action screen
color:#fff on background:var(--accent) (#0a84ff) computes to (1.0+.05)/(0.238+.05) ≈ 3.65:1. 16px semibold text does not qualify as WCAG "large text." This is the button for "Continue with N26," "Allow Access," "Start Monitoring," "Try Again," and — most importantly — "Save" on both Edit Rule screens, the button that commits the Good/Bad classification.
Fix: Darken --accent (e.g. toward #0068d6/#0060c0, ~4.5:1+ against white) or switch to dark text on a lighter accent tint; verify with a contrast checker.
high

--good/--bad pill and toggle text fails WCAG AA against their own tinted backgrounds, ~3.5–4.0:1

mocks/style.css .pill-good/.pill-bad/.toggle-btn — 01c, 04b, 04d, 02, 03, 06
--good (#1f9254, L=0.2149) on --good-bg (#e3f6ea, L=0.8820) = 3.52:1; --bad (#d5372e) on --bad-bg (#fbe6e4) = 3.97:1; --good directly on white --surface = 3.96:1 (--bad on white passes at 4.76:1). This is the literal "Good"/"Bad" pill text and the toggle-button label — the classification signal itself and the alert-reason pill render below the legibility bar for low-vision users.
Fix: Darken --good and/or lighten --good-bg (and similarly nudge --bad/--bad-bg) until the pair clears 4.5:1; re-check both the tinted-pill and plain-white-surface cases.
high

Core Good/Bad toggle and "Mark all Good" are markup-level <div>s with no button role

mocks/01c-classify-payees.html, 04b-payee-edit.html, 04d-payee-edit-bad.html
.toggle-btn and the "Mark all Good" row are plain divs with no href, role="button", or aria-pressed — outside the accessibility-tree focus order entirely. The real risk is a literal RN port (a bare View instead of Pressable/TouchableOpacity with accessibilityRole="button") making the single most important control in the app — deciding whether a payee is Good or Bad — unreachable by a screen-reader user. Whether it actually ships broken depends on coder-mobile's implementation, which the mock can't show.
Fix: When porting, make each toggle a Pressable with accessibilityRole="button" and accessibilityState={{selected: isActive}} (or a segmented radiogroup pattern), not a bare View.
medium

Payee-status avatar color is the only cue for a payee's own Good/Bad status on Debit List/Detail

mocks/02d-debit-search-results.html, 03b-debit-detail-over-limit.html, 02-debit-list.html
On the Rules screen every payee's status has both a colored avatar and an explicit pill — fully redundant. On Debit List/Detail the avatar communicates the payee's status by color alone; a deuteranope/protanope cannot reliably distinguish the muted green/red avatar tint at a glance, and there's no text fallback for that specific fact on this screen. Never causes a missed alert (the debit's own bad-ness is always separately pilled), but undercuts the "a trusted payee can still alert you" distinction the screen exists to show.
Fix: Add a small persistent text/shape cue tied to the avatar itself (e.g. a "trusted" label under the payee name, or a distinct border style for Good vs Bad).
medium

Nav-bar text links have no minimum touch-target sizing, unlike every other interactive class

mocks/style.css .nav-link — 03, 03b, 04b, 04d "‹ Back", 06 "Renew access early"/"Disconnect N26"
.nav-link sets only font-size/color/text-decoration — no padding or min-height, and its parent uses align-items:center rather than stretch, so the clickable box is genuinely just the text line-height (~18–20px), well under the 44px floor every other interactive class carries.
Fix: Give .nav-link the same treatment .search-clear got — a visible box plus an invisible hit-slop overlay to 44px — particularly for "‹ Back" and "Disconnect N26."
low

Settings toggle rows are far under the 44px floor

mocks/06-settings.html:32-43
"Push notifications" and "Group multiple alerts" rows use inline padding:2px 0 with no other height source — roughly 24–28px total row height vs 44px everywhere else interactive. Lower severity since this screen is an explicit stub.
Fix: Apply the same min-height:44px pattern used by .tx-row/.toggle-btn to these rows.
low

L(text-muted)=0.1571, L(neutral-bg)=0.8410, ratio ≈ 4.30:1. Both low-stakes: placeholder text disappears once typing starts, and "Off" is the inactive state of a non-critical toggle.
Fix: Darken --text-muted slightly or lighten --neutral-bg; only 0.2 short of passing.

Rendered as a static display row (plain divs, no label for/aria-labelledby/input), presumably because the numeric-entry state isn't among the 22 mocks. Not a confirmed defect, just an uncovered gap.

Settings "On"/"Off" pills are not marked up as a semantic switch

mocks/06-settings.html:32-43
pill-good/pill-neutral badges imply a toggle but carry no role="switch"/aria-checked equivalent; unclear from the mock whether these rows are even tappable yet (Settings is an explicit stub).

low

Modal overlay has no role="dialog"/aria-modal equivalent in the markup

mocks/06b-disconnect-confirm.html, 06c-delete-confirm.html
.modal-overlay/.modal-box are plain divs. Likely a non-issue in practice since React Native's native Modal handles focus containment correctly by default — worth a quick on-device check once built rather than assumed.
Fix: Verify RN's native Modal component is used (not a custom overlay) when this screen is built.
low

Small font sizes (11-13px) used for information that matters on a money app

mocks/style.css .tx-date, .pill, .notif-time
None illegible outright, but combined with the borderline text-muted contrast numbers above, they leave little margin for low-vision users. Static HTML/CSS can't show whether OS-level text scaling is respected.
Fix: When built, confirm containers don't clip text at larger accessibility font-scale settings; consider a 12-13px floor for anything conveying real information.
low

Syncing screen's status message isn't marked as a heading, no apparent live-region equivalent

mocks/01bb-syncing.html
"Fetching your debits" is a plain div, not a heading; the loading→done transition has no visible aria-live equivalent in the mock. Minor — a transient, auto-advancing screen.
Fix: Worth verifying the real state-announcement behavior on-device; not confirmable from a static mock.

The mocks are in good shape for the bulk of `REQUIREMENTS.md`: R9, R13/R13a, R14/R8a, R17/R17a,
R20/R20a wording, R23/R23a on the debit list, R25/R26/R26a's onboarding behavior, and the four

reconnect-gap resync) round out the findings; none of them touch literal on-screen copy the way
the R12a issue does.

## Findings

- **critical** R12a's "no rule" notification body is stale and self-contradictory across the two mocks that quote it (file: mocks/03-debit-detail.html:29, mocks/05-notification.html:24, requirement: R12a). Current `REQUIREMENTS.md` (revised 2026-09-24) fixes this exact string to `"You haven't reviewed this payee yet."`, specifically because the old wording falsely implied the payee itself was unfamiliar. `03-debit-detail.html`'s comment still reads `"This payee is new — you haven't reviewed it yet."`, and `05-notification.html`'s comment reads a third, different string: `"New payee — you haven't seen this one before."` Neither file was updated for the revision, and the two disagree with each other as well as with the spec. Because no mock screen for the "no rule" case is ever fully drawn (index.html's own notification group says only 5 and 5c, the "bad" and "over-limit" reasons, are drawn), these two comments are the *only* place the third reason's wording lives in `mocks/`, making this the single most likely spot to ship the wrong push copy. *Fix:* Replace both comments with the canonical `"You haven't reviewed this payee yet."` Consider drawing a `05a-notification-no-rule.html` mirroring 05/05c so all three R12a reasons have an actual rendered mock, not just prose.

- **medium** `05b-notification-summary.html`'s explanatory comment uses the exact terminology R10b explicitly forbids (file: mocks/05b-notification-summary.html:19-20, requirement: R10b/R20). It reads "every charge from the gap carries a **transaction ID** the app has never seen," but R10b was revised specifically to say the identifier is `(connected account, entry_reference)` and that `transaction_id` "may change between fetches and is not guaranteed unique" and must **never** be used. The comment restates the exact mistake the requirement was rewritten to correct. *Fix:* reword to "every charge from the gap carries an identifier (`entry_reference`) the app has never seen."

- **medium** `01bb-syncing.html` cites the wrong requirement for why first-sync debits don't notify (file: mocks/01bb-syncing.html:20, requirement: R25). The footer reads "Nothing fetched here notifies — the first sync is stored as already-seen (**R10b**)." R10b only defines the de-duplication identifier; the rule that first-sync debits are already-seen and can't notify is R25 (added 2026-09-24), which R10c's own "Consequences" list explicitly attributes to R25, not R10b. The citation predates R25's existence and was never updated once R25 was carved out to own this behavior. *Fix:* change the citation to `(R25)`.

- **medium** `05b-notification-summary.html`'s footer reuses the defined term "first sync" for an ordinary reconnect resync, blurring the exact distinction R20b was added to police (file: mocks/05b-notification-summary.html:34, requirement: R20/R20b/R25). It reads "Sent once, right after **the first sync** following a reconnect." R25 defines "first sync" as a specific, one-time event (the bulk pull right after granting consent, or its resumption); R20b exists precisely because an *ordinary* reconnect (after a mere disconnect or expiry) must route through R20's gap-summary path, never through R25's silent first-sync path — only a reconnect after account deletion re-enters R25. Calling the post-reconnect resync "the first sync" invites exactly that conflation. *Fix:* reword to "Sent once, right after the app resyncs following a reconnect" (or similar), avoiding the term "first sync" for this event.

- **medium** No mock demonstrates the Rules-list search states R23b explicitly requires parity for (file: mocks/04-payee-rules.html, requirement: R23/R23b). The debit list gets both a no-match state (`02c`) and a filtered-results-with-grouping state (`02d`), and `index.html`'s own commentary calls `02d` "the one that carries the rule worth getting right." R23b says explicitly that the Rules tab "get[s] the same guarantee, not just the one with a detail screen," yet `04-payee-rules.html` only shows the search field empty/unfocused — there is no drawn no-match or filtered-results state for the Rules list, so a builder has no visual reference for that half of R23/R23b. *Fix:* add a `04e`-style pair (or at least a filtered-results variant) mirroring `02c`/`02d` for the Rules list.

- **low** Onboarding copy undersells R25's "as much as the ASPSP returns" scope by calling the first-sync pull "recent history" (file: mocks/01bb-syncing.html:15, mocks/01c-classify-payees.html:14, requirement: R25). R25 is explicit that the first sync is "one bulk pull of the account's available history — as much as the ASPSP returns; there is no separate 'how far back' setting." Both mocks instead say "we're pulling your **recent** history" and "We found 5 payees in your **recent** history," which reads as a bounded recency window rather than full available history — a minor mismatch, unlikely on its own to cause a coded bug since the backend already pulls full history, but worth tightening since it's user-facing copy. *Fix:* reword both to "your account history" / "your available transaction history," dropping "recent."
